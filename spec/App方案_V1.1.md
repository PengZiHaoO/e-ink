## 1. App 形态：三屏轻工具

### 1.1 三屏

```text
┌─ 屏1：状态选择（首页）────────────┐
│  [ 专注 ]  [ 休息 ]  [ 可打扰 ]     │
│  [ 离开 ]  [ 名片 ]  [ 自定义… ]    │
│                                   │
│  点「专注」→ 可补一句自定义文字      │
│  （如 "15:30 后可打扰"，可不填）     │
└───────────────────────────────────┘
              ↓
┌─ 屏2：预览 + 写入 ────────────────┐
│   卡片最终效果预览（1-bit 模拟）     │
│   「翻转手机，贴住卡片」             │
│   → NFC 写入（iOS 系统弹窗一闪 /    │
│     Android 静默）→ ✓ 完成          │
└───────────────────────────────────┘
              ↓
┌─ 屏3：专注记录 ───────────────────┐
│   今日 2h14m ｜ 3 次 ｜ 最长 47m    │
│   连续 5 天                         │
│   （会话列表：开始/结束/时长）        │
└───────────────────────────────────┘
```

### 1.2 V1 明确不做

- 账号 / 登录
- 社区 / 素材市场（那是 G Shell 的路，重运营，与专注定位不符）
- 后台推送 / 自动更新
- GIF / 动态内容

### 1.3 状态 = 用户手动填充（平台能力天花板）

> **iOS 没有公开 API 让第三方 App 读取专注模式状态；两端都无法后台写 NFC。**
> 所以"自动同步系统状态"不存在——这不是妥协，是天花板，也恰好符合产品极简出发点。

记录闭环靠**用户自己的两次点按**：

```text
点「专注」→ 写卡成功 → App 记时间戳（开始）
点「休息/结束」→ 写卡成功 → 记时间戳（结束）→ 时长入账
```

忘点结束 → 下次打开 App 提示补记："上次 14:32 开始的专注还没结束，现在结束吗？"

### 1.4 半自动的天花板（V1.5 可选）

| 平台 | 能做到的极限 |
| --- | --- |
| iOS | 快捷指令自动化：专注模式开启 → **打开 App 并预选"专注"** → 用户仍需翻转写卡 |
| Android | 监听勿扰模式（zen mode）→ 同样只做**预选**，写卡仍需前台 |

**自动化只到"帮你打开 App、选好状态"，最后一下翻转永远是用户的**——反而保住仪式感。

## 2. 先纠正一个关键误传

> **"iOS 不支持第三方 NFC 写入"——这是错的。**

- **iOS 13+ 的 Core NFC 支持第三方 App 写 NDEF**（`NFCNDEFReaderSession` + `tag.writeNDEF`）。
- 误传来源：iOS 只支持 **NDEF 格式**、不支持 MIFARE Classic 等原始标签写入——被简化成了"不支持写入"。
- **铁证**：极稚的 iPhone App（G Shell）就是靠 Core NFC 往手机壳背面的标签写图的，出货 10 万+。
- 我们使用的 NT3H / ST25DV 都是 NDEF 标签，**双端写入可行**。

---

## 3. 两端 NFC 能力与差异（核心约束）

| 能力 | iOS（Core NFC） | Android（android.nfc） |
| --- | --- | --- |
| NDEF 读取 | ✅ 13+ | ✅ 全系 |
| NDEF 写入 | ✅ 13+（`writeNDEF`） | ✅ 全系（`Ndef.writeNdefMessage`） |
| 原始 / MIFARE | ❌ 不支持 | ✅ 支持（我们用不上） |
| 读取系统专注/勿扰状态 | ❌ **无公开 API** | ⚠️ 可读 zen mode（仅用于预选） |
| 后台标签读取 | ⚠️ 只读、仅 URI、需亮屏 | ✅ 后台 intent 派发 |
| 后台写入 | ❌ 不存在 | ❌ 不存在 |
| 写入交互 | **系统扫描弹窗**（必须前台会话，一次只能一个） | 静默 reader mode / 前台派发 |
| 其他坑 | 需 entitlement + `NFCReaderUsageDescription`；会话不可复用 | 机型天线位置碎片化；部分机型（三星）耦合弱 |

**对本产品最重要的三点：**

1. **iOS 写入必须有系统弹窗**（"Ready to scan"扫描界面，一闪而过）——"翻转即更新"的仪式感设计要把这个弹窗算进去，不是 Bug，是平台规则。
2. **两端都不存在"后台自动写入"**——卡片更新必然由"用户点一下 + 一次翻转"触发。**不要在产品里承诺"自动更新"**（与软件方案"不宣传实时通知"一致）。
3. **标签在你自己手机背上**——会话一开始就"发现"它（永远在场），不需要"找标签"交互；但耦合靠天线对齐，这就是 EVT-2 翻转姿态要测的东西。

## 4. 本项目特有的情况：写"自己背上的标签"

```text
卡片贴着手机 → 标签永远在 NFC 场内 → 会话开始即发现 → 写入
                     │
                     └─ 但耦合靠天线对齐，翻转姿态是关键（EVT-2）
```

- **优势**：无需"寻找标签"的交互，App 一发起就命中。
- **风险**：标签天线必须与手机 NFC 读头位置对齐（iPhone 读头在背面上方）。
- **Apple Pay 冲突**：卡片标签贴着手机可能干扰支付 NFC。**极稚用红色禁用按钮解决（用户痛点），我们应在硬件上规避**（天线位置 / 铁氧体隔磁 / 检测到支付时自动降级），不要把它留给用户去按。

## 5. 框架选型：Flutter + nfc_manager

| 方案 | NFC 支持 | 适用 | 建议 |
| --- | --- | --- | --- |
| **Flutter + `nfc_manager`** | ✅ 两端 NDEF 读写，活跃维护 | 单代码库、UI 定制强、小团队 | **默认选它** |
| React Native + `react-native-nfc-manager` | ✅ 两端 NDEF | 团队熟 JS/RN | 备选 |
| 纯原生（Swift + Kotlin） | ✅ 最底层控制 | NFC 极其复杂 / 要后台能力 | 暂不需要，成本高 |

选型与出发点的匹配：App 是"三屏轻工具"，UI 轻、逻辑轻，唯一的平台差异重活（NFC 会话）恰好被 `nfc_manager` 抹平；NFC 写卡核心逻辑两端共用，Android 验证过的东西迁移 iOS 成本低。

`nfc_manager` 核心流程：

```text
检查可用 → startSession（iOS 弹窗 / Android 静默）
        → 发现标签（卡片，永远在场）
        → queryNDEFStatus（查可写 / 容量）
        → writeNDEF
        → stopSession（所有分支都要调，否则 iOS 弹窗卡死）
```

**架构硬规矩：NFC 层独立封装成模块**，内含：会话管理、写失败重试、容量检查、错误回调。UI 与状态机永不直接碰 NFC API——将来换原生 / 升级插件都不动业务代码。

## 6. App 架构

```text
┌───────────────────────────────────┐
│ UI 层（状态选择 / 预览写入 / 记录） │
├───────────────────────────────────┤
│ 状态机（五态 + 打点事件）           │ ← 单例，本地持久化
├───────────────────────────────────┤
│ CardRenderer(profile,…) → 位图     │ ← 生成 NDEF payload
│ 硬件抽象：DeviceProfile / 协议编解码 │ ← 硬件无感边界（支持多代硬件）
├───────────────────────────────────┤
│ CardWriter（会话 / 重试 / 错误码）  │ ← 唯一碰 NFC API 的地方
│   ├─ MockWriter（桌面）            │
│   └─ NfcWriter（真机 nfc_manager） │
├───────────────────────────────────┤
│ 本地存储（会话/设置/streak/绑定）   │
└───────────────────────────────────┘
```

### 数据流（一次"开始专注"）

```text
屏1 点「专注」（可填自定义文字）→ 状态机进入 Focusing
  → 屏2 渲染引擎生成 "FOCUSING 14:32" 1-bit 位图（预览）
  → RLE 压缩（几百 B ~ 几 KB）
  → 包成 NDEF payload（Header/Version/DeviceID/ImageSize/CompressionType/ImageData/CRC）
  → 用户翻转贴卡 → NFC 模块写入（iOS 弹窗一闪 / Android 静默）
  → 写成功 = 打点：状态机持久化记录（开始时间戳）
```

### ⚠️ NFC 芯片内存约束（与硬件 BOM 挂钩）

NDEF 写入时 payload 要先落在标签 EEPROM 里：

| 芯片 | 用户内存 | 能否装下 4.7KB 位图 |
| --- | ---: | --- |
| NT3H2111 | 888 B | ❌ |
| NT3H2211 | 1912 B | 仅文字型可 |
| **ST25DV64K** | **8 KB** | ✅ 推荐 |

**规格约束：payload 必须 < 芯片可用内存。** 这会反过来约束 App 的压缩率，选型时把 ST25DV64K 作为首选。

└────────────────────────────────┘
┌─ 艺术家（素材市场）──────────────┐
│  插画师成品模板：动漫/体育/文字语录  │

### 8.2 核心流程

```text
首次：App 首页点「开始配对」→ NFC 连接（识别不到按红色长条辅助）

换图：相册/拍照 → 裁剪 → 预览墨水屏效果 → 「去投屏」→ NFC 一贴 → 刷新
      （全程约十几秒到半分钟）
```

- 支持静态图（照片/插画/表情包/壁纸），不支持 GIF
- NFC 读写每次 1~2 秒；无电池，电容储能；图案 0 功耗永久显示
- 红色按钮临时禁用 NFC 以便刷卡（Apple Pay 冲突的被动处理）

### 8.3 AI 生图 + 点数制

- 拍照实景 / 相册导入 → AI 自动墨水屏化（点阵化、适配圆形屏）
- 风格：贴纸 / 盲盒 / 3D 头像
- **点数制**：激活送 100 点、每日登录 15 点、生图每次 3 点；另有 PRO 会员
- 后续规划：自定义文字、更多 AI 风格

### 8.4 战略拆解

G Shell 是**内容平台型 App**，不是工具：

| 设计 | 背后的判断 |
| --- | --- |
| 素材市场 + 社交 + AI 生图 | 卖"换装"心智，App 是内容分发场 |
| 每次手动选图传图 | 没有"状态"概念，一切都是"选一张图换上去" |
| 点数制 + PRO 会员 | AI 是变现钩子，社交是留存钩子 |
| 实时"上壳效果"预览 | 降低"图放上去好不好看"的决策成本 |
| 无状态机 / 无行为记录 / 无后台 | **不碰"你的状态/行为"，只碰"你的图"** |

### 8.5 借鉴 & 避开

**借鉴（不照抄）：**

1. **"预览再投屏"的流畅 UI** —— 我们对应"状态卡预览 → 翻转 → 更新"。
2. **AI 一键生成** —— 它生成"图"，我们生成**"状态模板"**。
3. ⚠️ **红色禁用按钮 = 真实痛点** —— 证明 Apple Pay 冲突是硬问题；我们在硬件上规避，不学它留给用户按。

**避开（机会空间）：**

| 维度 | G Shell（极稚） | 我们的专注卡 |
| --- | --- | --- |
| 心智 | 换装 / 表达 | 行为管理 / 状态 |
| 核心对象 | 图片 | 状态机 + 记录 |
| 使用频率 | 偶尔换图 | 每天多次（开始/结束专注） |
| 数据 | 无行为数据 | 专注记录 / streak / 统计 |
| 传输 | 手动选图传图 | 翻转即更新（状态驱动） |
| 后台能力 | 无 | 本地记录 + 可选云同步 |

> 极稚证明了两件事：① NFC 写图链路在 iPhone 上跑得通（放心做）；② "内容+社交"是重运营且与专注定位不冲突。**我们不抄它的内容平台，抄它的流畅传输体验，用"状态机 + 记录"做护城河。**

## 10. 关键风险清单

1. **iOS 系统弹窗**：写入必须前台会话，弹窗一闪而过——设计成"翻转仪式"的一部分，别让它像 Bug。
2. **无自动同步**：后台写入两端都不存在 + iOS 无专注模式读取 API——**状态永远由用户手动填充（或快捷指令预选），不承诺自动更新**。
3. **写失败/超时**：标签在背上但耦合偶尔差——NFC 模块必须有重试和友好错误提示。
4. **Apple Pay 冲突**：用天线位置/隔磁/检测降级规避，不学极稚的红色按钮。
5. **机型兼容**：Android 天线位置碎片化（三星等耦合弱）、iOS 较统一——用 EVT-3 机型矩阵回归 App。

## 11. 开发环境配置（WSL2 · Ubuntu 24.04）

### 11.1 两个硬约束

1. **iOS 构建必须 macOS** → WSL2 内只做 Android；iOS 用 Mac 或云构建（Codemagic / GitHub Actions macOS runner），且真机 iPhone 实测不可省（系统扫描弹窗体验必须实机确认）。
2. **NFC 无模拟器** → iOS Simulator / Android Emulator 都没有 NFC 硬件，**必须真机调试**。

### 11.2 安装布局

| 组件 | 位置 | 方式 |
| --- | --- | --- |
| JDK 17 | `/usr/lib/jvm/java-17-openjdk-amd64` | apt |
| Android SDK | `~/android-sdk` | cmdline-tools + sdkmanager（platform-tools / build-tools 35 / platforms 34+35） |
| Flutter | `~/flutter` | 官方 stable tar.xz |
| 环境变量 | `~/.bashrc`（`flutter_dev_env` 段） | JAVA_HOME / ANDROID_HOME / PATH |

### 11.3 真机连接：WiFi adb（推荐，绕开 USB 透传）

```bash
# 手机：设置 → 开发者选项 → 无线调试
adb pair <手机IP>:<配对端口>     # 输入手机上显示的配对码
adb connect <手机IP>:<调试端口>
flutter devices                  # 应能看到手机
```

> usbipd-win USB 透传可行但坑多；WiFi adb 十分钟搞定，且 NFC 调试不受影响——NFC 是手机自身硬件，与调试通道无关。

### 11.4 验证

```bash
flutter doctor    # Android toolchain 项全绿即可开工
```
